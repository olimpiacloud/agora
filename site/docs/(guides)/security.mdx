Agora controls a real computer with logged-in browser sessions. Treat access to it like SSH access to the host.

## Network exposure

- The daemon listens on **127.0.0.1:7788** and refuses to bind to any other interface unless you set `AGORA_ALLOW_PUBLIC=1`. Don't.
- For remote access, publish it through an **authenticated tunnel** (for example Cloudflare Tunnel with Access, or an SSH tunnel). Never open the port to the internet.
- Chromium is controlled with `--remote-debugging-pipe`: **there is no CDP TCP port**. X displays are local to the host and never exposed.
- WebRTC needs UDP to the host. Behind HTTP tunnels, viewers use the WebSocket transport instead.
- The embedded dashboard is served with a strict Content Security Policy (`default-src 'self'`).

## Tokens

Every API call needs `Authorization: Bearer <token>`. Streaming endpoints also accept a viewer token as `?token=` because browsers cannot set headers on WebSocket and `<img>` requests. Admin and cursor tokens are refused in the query string so they never end up in proxy logs or browser history.

| Token | Scope | Where it comes from |
| --- | --- | --- |
| Admin | Everything. | Generated on first start in `admin.token` (mode 0600). `agora token` prints it. |
| Cursor | Its own workspace and its own descendants, limited by its permissions. | Returned once by `POST /v1/cursors`. Agora stores only a hash. |
| Viewer | Streaming one workspace, with or without input, for at most 24 hours. Rejected on every other endpoint. | `POST /v1/viewer-tokens` or `agora open`. HMAC-signed with `viewer.key`. |

Give agents cursor tokens, never the admin token. Permissions only narrow down the tree: a child can never get a permission its parent lacks, and only cursors with `workspace` can create workspaces, freeze, suspend, fork or take control.

## Process isolation

- When the daemon runs as root, **apps and browsers run as the unprivileged `agora` user** (home `/var/lib/agora-apps`), with no access to root's files.
- **Chrome's sandbox stays on.**
- Each workspace has its own processes, display and (by default) browser profile. Processes start inside a per-workspace cgroup when cgroups v2 is available, which enforces `memory_mb` and `cpu_percent` budgets.
- Request bodies are capped at 8 MB.

## What Agora does not isolate

Isolation between cursors **in the same workspace** is logical: tab owners, surface locks and token scopes. They share one display, one browser profile and one Unix user. A cursor with `browser` permission can read any page in that profile.

For agents you do not trust:

- Put them in **separate workspaces** (separate processes, display and profile), and do not give them the `workspace` permission.
- Turn on [`sandbox`](#sandboxed-workspaces) for those workspaces, so their browser and apps cannot read the rest of the host.
- Use a dedicated profile without your personal logins.
- Keep `process` and `desktop` off unless the task needs them: `process` launches programs as the `agora` user.

Agora does not checkpoint memory: a suspended workspace keeps cookies and storage on disk in its profile, not open page state.

## Sandboxed workspaces

New workspaces are sandboxed by default (`agora serve --sandbox-default`, on unless you turn it off): their Chrome and every app launched in them run in a confined view of the host. Only the admin can create an unsandboxed workspace, with `"sandbox": false` in its `config`; workspaces created before the default keep their stored setting. To request it explicitly:

```bash
agora api POST /v1/workspaces '{"name":"untrusted","start":true,"config":{"sandbox":true}}'
```

Each sandboxed process starts through `agora sandbox-exec`, which runs it in new mount, PID, IPC and UTS namespaces:

- The whole system is mounted read-only and without setuid bits.
- Home directories, `/tmp`, `/run`, `/var/lib` (which holds the Agora state, Docker and databases), `/var/log` and the Agora home directory are hidden behind empty mounts.
- Only the workspace's own directory, its Chrome profile and its X socket are mounted read-write.
- The workspace gets a private `/tmp`, `/dev/shm` and `/proc`. Its apps cannot see, signal or trace processes of other workspaces. Apps of an unsandboxed workspace share the host's process view and run as the same apps user, so they can signal processes of other workspaces, sandboxed or not.
- The process runs as the unprivileged apps user, with no supplementary groups and no capabilities. Chrome's own sandbox keeps working inside.

Limits:

- **Root only.** The daemon must run as root with an apps user (the default for `agora.service`). Otherwise a sandboxed workspace fails to start.
- **Shared network.** Sandboxed processes can reach services on `127.0.0.1`, including the Agora API (which still needs a token). Do not run unauthenticated local services next to untrusted workspaces.
- **Shared display.** Xvfb runs outside the sandbox (as the dedicated `agora-x` user, neither root nor the apps user), and X11 does not isolate clients on the same display: every app in the workspace can read the screen and send input to every other window of that workspace.
- **Readable system files.** World-readable files in `/etc` and `/usr` stay readable. Keep secrets out of them.
- **Same user, same kernel.** A kernel exploit escapes the sandbox. For hostile code, use a VM or a separate machine.
- **Launched agents are not sandboxed.** Agents started by `cursor_spawn` (`claude`, `codex`) run as the daemon user, because they need its credentials. The sandbox covers Chrome and `desktop_launch` apps only.
- **No D-Bus.** `/run` is hidden, so apps that need the system or session bus lose those features.
- CPU and memory limits come from the workspace `budget`, not from the sandbox.
